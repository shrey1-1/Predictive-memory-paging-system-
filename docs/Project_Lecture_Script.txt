PREDICTIVE MEMORY PAGING SYSTEM WITH WORKLOAD AWARENESS
A complete spoken lecture on the project


PART ONE. THE BIG PICTURE.

Welcome. In this lecture I am going to teach you your entire project, from the very first idea to the final results, as if we were sitting together in a classroom. You do not need to look at anything while you listen. I will explain every idea in words, build it up slowly, and connect every piece to the pieces around it. By the end, you should be able to explain this project to anyone, defend every design decision, and answer difficult questions about it.

Let's start with the question every good project begins with. What problem are we solving?

Every program running on a computer needs memory to hold its data. A computer has two very different kinds of storage. The first is the main memory, usually called RAM, which stands for random access memory. RAM is extremely fast, but it is small and expensive. The second is the disk, which might be a traditional hard disk drive or a modern solid state drive. The disk is huge and cheap, but it is enormously slower than RAM. Reading something from a disk can take thousands of times longer than reading it from RAM.

Because RAM is small, the operating system cannot keep all of a program's data in RAM at once. So it keeps the data the program is using right now in RAM, and it leaves everything else on the disk. Data moves between the disk and RAM in fixed-size blocks called pages. In this project, every page is four kilobytes, which is about the size of two pages of printed text.

Now here is the problem. When a program asks for a page that is not currently in RAM, the program cannot continue. It has to stop and wait while the operating system fetches that page from the slow disk. This event is called a page fault. A page fault is the moment of waiting. The more page faults a program suffers, the more time it spends waiting instead of working.

Let me give you an analogy that we will use throughout this lecture. Imagine a student studying at a small desk in a very large library. The desk is RAM. Only a few books fit on it, but any book on the desk can be read instantly. The library shelves are the disk. Every book exists somewhere on the shelves, but walking to the shelves to fetch a book takes a long time. A page fault is the moment the student realises the book they need is not on the desk, stands up, and walks to the shelves. And when the desk is full, the student must put some book back on the shelf to make room for the new one.

Traditional operating systems handle this situation in a purely reactive way. They wait until a page fault happens, then they fetch the missing page, and if RAM is full they choose some page to throw out. The rule that decides which page to throw out is called the page replacement policy, or the eviction policy. Familiar examples are FIFO, LRU and Clock, which I will explain shortly.

The idea behind this project is to be proactive instead of reactive. What if the system could predict which pages the program will need next, and bring them into RAM before the program asks for them? If the prediction is correct, the page is already waiting in RAM when the program needs it, and the page fault simply never happens. Bringing pages in early like this is called prefetching.

But here is the catch, and it is the heart of this entire project. Prefetching is a bet. When RAM is full, every page you bring in early forces some other page out. If your guess is right, you win: you avoided a fault. If your guess is wrong, you have wasted a disk read, and worse, you may have thrown out a page the program actually needed soon. That thrown-out page will now cause a fault that would never have happened if you had done nothing. In other words, a careless prefetcher can make the system slower than doing nothing at all.

Go back to the library. Imagine the student has a helper who brings books the student will probably need next. A good helper saves the student many trips to the shelves. But the desk is small. Every book the helper brings pushes another book back to the shelf. A helper who guesses badly fills the desk with useless books and pushes away the ones the student was using, so the student ends up walking to the shelves more than before.

So the project needs two things. It needs a predictor, which guesses the next pages. And it needs a decision engine, which decides, for each guess, whether acting on it is worth the risk. The decision engine also needs a way to learn from experience: it must measure whether prefetching is actually helping, and become bolder or more careful accordingly. That learning loop is called feedback, and as you will see, choosing the right feedback signal turned out to be one of the most important findings of the project.

What exactly did the project build? It built a simulator, written in the Python programming language. A simulator is a program that imitates a real system. Instead of modifying a real operating system, which would be extremely complicated, we record the sequence of pages that real programs asked for, and we replay that sequence through software models of RAM, eviction policies, predictors and decision engines. We count how many page faults each approach causes, and later we also estimate how long each approach would take.

And what did we find? I will give you the headline now, and we will spend the rest of the lecture understanding where it comes from. On twenty-two real benchmark programs, each tested with two memory sizes, so forty-four tests in total, the final system removes on average fifty-five percent of the page faults that the standard LRU policy suffers. The simple readahead method used by Linux removes about fifty-one percent, and a pure pattern-learning Markov predictor removes only about eight percent. The final system is worse than LRU in only one of the forty-four tests. But when we estimate actual running time, the final system is about one point four three times faster than LRU on a fast solid state drive, which is essentially the same as Linux readahead, and on a traditional hard disk every prefetching system is actually slower than LRU. So one of the most important lessons is that fewer page faults do not automatically mean a faster program. Keep that in mind; we will come back to it.


PART TWO. THE FOUNDATIONS.

Before we can understand the system, we need to understand the basic ideas it is built from. Let's take them one at a time.

First, pages and frames. A page is a four kilobyte block of data. A frame is a slot in RAM that can hold exactly one page. If we say RAM has twenty-one frames, it means RAM can hold twenty-one pages at once. Every memory address can be turned into a page number by dividing the address by four thousand and ninety-six, which is the number of bytes in a page. In the code this is done with a bit shift: the last twelve bits of the address are dropped, because two to the power of twelve is four thousand and ninety-six. So all the addresses inside the same four kilobyte block map to the same page number.

Second, the working set. The working set of a program is the collection of all the distinct pages it uses. For example, one of our real programs, a fluid simulation called leslie3d, uses two thousand one hundred and thirty-four different pages during the part we recorded. This matters because of an important design rule in the project: RAM is always sized as a percentage of each program's working set, usually one percent or five percent. For leslie3d, one percent of two thousand one hundred and thirty-four is twenty-one frames. Why not just use a fixed size like one thousand frames? Because if RAM is large enough to hold everything, nothing is ever evicted, every policy behaves identically, and there is nothing to compare. The early experiments discovered exactly this: with fixed frame counts, one program gave identical results under every policy. So memory must be scarce for the experiment to mean anything.

Third, eviction policies. When RAM is full and a new page must come in, some resident page must leave. Let me explain the six policies the project implements.

FIFO stands for first in, first out. It removes the page that arrived in RAM earliest, like a queue. In the library, it means putting back the book that has been on the desk the longest, regardless of whether you are still using it.

LRU stands for least recently used. It removes the page that has gone the longest without being used. In the library, it means putting back the book you have not opened for the longest time. LRU is the standard choice and it is the main baseline in this project. Every percentage I quote compares against LRU.

Clock is a cheap approximation of LRU that real operating systems use. Imagine the pages arranged in a circle with a clock hand pointing at one of them. Each page has a reference bit that is set when the page is used. When a victim is needed, the hand moves around the circle. If the page under the hand has its bit set, the hand clears the bit, giving the page a second chance, and moves on. The first page found with a cleared bit is evicted.

OPT, also called Belady's optimal algorithm, removes the page whose next use is furthest in the future. This is mathematically the best possible eviction policy. But it is impossible in a real system, because the operating system cannot see the future. In a simulator, however, we have the whole recorded sequence, so we can compute OPT. That makes OPT a yardstick: no eviction policy can ever do better than OPT.

LRU-2 looks at the second most recent use of each page instead of the most recent one. Pages that have been used only once are evicted first. This helps against one-time scans through data.

ARC stands for adaptive replacement cache. It keeps two lists, one for pages seen once recently and one for pages seen at least twice, and it also remembers the identities of recently evicted pages, called ghost entries, to decide how to balance recency against frequency.

Let me make this concrete with a small example that the project actually computed by running its own code. Imagine RAM has three frames, and the program requests the pages one, two, three, one, four, one, two, five, one, two. The first three requests all fault because RAM starts empty, and RAM now holds pages one, two and three. The fourth request, page one, is a hit. The fifth request, page four, faults, and RAM is full, so something must leave. FIFO evicts page one, because page one arrived first, even though page one is about to be used again. LRU evicts page two, because page two is the least recently used, since page one was just touched. OPT looks into the future, sees that page three is never used again, and evicts page three. If you follow the rest of the sequence, FIFO ends with seven faults, LRU with six, and OPT with five. OPT wins because it sees the future.

Fourth, compulsory faults. The very first time a program asks for a page, that page cannot possibly be in RAM unless something loaded it early. That first-touch fault is called a compulsory fault. No eviction policy can avoid it, not even OPT. This is the key reason prefetching is interesting: prefetching is the only way to avoid compulsory faults. And it explains a result that surprises many people: our prefetching system sometimes has fewer faults than OPT. That does not break the rule that nothing beats OPT, because OPT is the best only among eviction policies. A prefetcher plays a different game.

Fifth, traces and trace-driven simulation. A trace is a recording of the memory requests a real program made, in order. The project uses publicly available traces from a research competition on data prefetching, called the ML-Based Data Prefetching Competition. These traces come from well-known benchmark suites. SPEC CPU 2006 is a standard collection of scientific and engineering programs, including fluid simulations like bwaves and leslie3d, a physics simulation called milc, a quantum computing simulation called libquantum, a route-planning program called mcf, and others such as soplex, omnetpp, astar, GemsFDTD, lbm and sphinx3. GAP is a collection of graph algorithms, including breadth-first search, called bfs, PageRank, called pr, betweenness centrality, called bc, connected components, called cc, and single-source shortest paths, called sssp. In total, twenty-two real traces were used, each capped at two hundred thousand requests.

There is an honest caveat you must always mention. These traces were recorded at the level of the processor's last-level cache, which is a small fast memory inside the processor. They are not recordings of real operating-system page faults. By mapping their addresses to four kilobyte pages, we get a good approximation of paging behaviour, but it is an approximation.

The project also uses six synthetic traces, which are made-up patterns where we know the right answer in advance: a sequential scan, a strided pattern that jumps by eight pages each time, a small repeating loop called cyclic, a clustered pattern that hops randomly inside a group of ten pages and then moves to a new group, a completely random pattern, and a phase-changing pattern that switches from sequential to cyclic to random. These synthetic traces act as tests. For example, a sequential scan with no prefetching must fault on every single request, and if it ever did not, we would know the simulator was broken.

Why use simulation at all instead of a real system? Three reasons. Every method sees exactly the same input, so the comparison is perfectly fair. The results are reproducible, so anyone can rerun them and get identical numbers. And only a simulation can compute OPT, because OPT needs the recorded future.

Sixth, the warm-up rule. Every trace is split in time order. The first twenty-five percent is called the warm-up portion. Here is the rule that runs through the whole project: any setting, any parameter, any design choice may only be chosen by looking at the warm-up portion. The full traces are then used once, to evaluate. Why does this matter? Because if you tune your system on the same data you test it on, your results look better than they really are. It is like a student who sees the exam questions in advance. The project treats this as a hard rule.


PART THREE. THE ARCHITECTURE.

Now that we have the foundations, let's look at how the system is organised. I will describe the architecture as a set of components and the information that flows between them.

At the start of the pipeline is the trace, a long list of page numbers in the order the program requested them. The simulator reads this list one request at a time.

Each request first goes to the memory engine. The memory engine models RAM. It keeps a set of resident pages, meaning the pages currently in RAM. It answers one question: is this page resident? If yes, it is a hit. If no, it is a page fault, and the memory engine must bring the page in, asking the eviction policy for a victim if RAM is full. In the final system, the eviction policy underneath is LRU.

Next comes the predictor. The predictor watches the stream of requests, learns patterns from it, and after each request proposes candidate pages that it expects to be needed soon. Each candidate comes with a confidence, a number between zero and one that says how sure the predictor is.

Each candidate then goes to the decision engine. The decision engine looks at the candidate's confidence and at the state of memory and answers yes or no: should we prefetch this page now?

If the answer is yes, the candidate goes back to the memory engine and is loaded into RAM. And here is a crucial design rule. Prefetched pages enter RAM through exactly the same internal routine as pages loaded because of a fault. There is only one door into RAM. Why does this matter? Because it guarantees correctness. A predictor can never corrupt the memory model; at worst, a terrible predictor makes the system slower. If you switch prediction off entirely, you are left with a perfectly correct plain LRU simulator.

Running alongside all of this is the feedback loop. In the final system, a component called the shadow directory replays exactly the same requests, but without any prefetching. It is a copy of the eviction policy that stores only page identifiers, not page data. Because it sees the same requests but never prefetches, it tells us how many faults we would have had without prefetching. Every one thousand requests, a feedback controller compares the faults of the real system with the faults of the shadow. The difference is called the fault delta. If prefetching saved faults, the controller makes the decision engine bolder. If prefetching caused faults, it makes the decision engine more careful.

Finally, the memory engine can record an event log, a list of every fault, every prefetch, and every first use of a prefetched page. A separate component called the time model replays that event log on a simulated disk to estimate running time.

There is one more architectural principle worth understanding. The predictor and the decision engine never see each other's internals. The predictor only ever sees the history of requests; it never sees what is in RAM. The decision engine only ever sees a candidate page, its confidence, and simple facts about memory such as how many frames are free; it never sees the predictor's tables. Why was this done deliberately? Because it lets us swap components independently. In the project, nine different decision engines were compared on byte-for-byte identical predictions, so any difference in results could only come from the decision engine. That kind of clean comparison is what makes the findings believable.

Now let me tell you how the code is organised, so you can connect this architecture to real files. The library lives in a folder called source, paging, and it has eight modules. The config module holds paths and all the frozen settings. The traces module generates synthetic traces, converts real traces and loads them. The engine module contains the memory engine and all six eviction policies. The predictors module contains every predictor. The deciders module contains every decision engine and the shared feedback controller. The simulate module contains the main loops that run a trace through the whole system with different kinds of feedback. The timing module contains the time model. And the final module wraps the final system into a single function called run final. Around the library sit numbered scripts, one per experiment, a test file, and the documents.


PART FOUR. THE COMPLETE EXECUTION FLOW.

Let's follow what happens inside the system from the moment you start it.

You run a script, for example the robustness script or the script called run all that runs everything. The script first adds the library folder to Python's search path and reads the configuration, which says where the data and results folders are.

The script then loops over the traces it is configured to use. For each one, it checks whether the trace file exists in the data folder. If a trace is missing, the script prints a message and skips it, so everything still works with only the synthetic traces. If the trace exists, it is loaded: the comma-separated file is read, the first two hundred thousand page numbers are kept, and they are wrapped in a trace object that also stores the gaps between consecutive pages and the position where the warm-up portion ends.

Next, memory is sized. The script counts the distinct pages in the trace and takes one percent, or five percent, with a minimum of eight frames.

Then the system is built: an LRU policy object, the final predictor, and the final decision engine. And then the main loop begins. Let's follow one single request through that loop, step by step, because this loop is the beating heart of the project.

Step one. The next requested page is taken from the trace. The simulator first notes whether this page was a prefetched page that has not been used yet. Then it calls the memory engine's access function. Inside, the request counter goes up. If the page was waiting in RAM because of an earlier prefetch, that prefetch is now counted as used. If the page is resident, the policy is told about the hit, so LRU moves the page to the most recently used position. If the page is not resident, the fault counter goes up and the page is installed.

Step two, at the same moment, the same page is also passed to the shadow directory, but only if the page belongs to the sample the directory tracks. In the final system the sample is every page. The shadow directory has its own copy of LRU and never prefetches, so it counts the faults we would have had without prefetching.

Step three. The simulator tells the decision engine about outcomes. If a prefetched page was just used, that is reported. If any prefetched pages were evicted without ever being used, those are reported as wasted.

Step four. If the number of requests so far is a multiple of the epoch length, which is one thousand in the final system, the feedback controller runs. It computes the fault delta for the epoch and moves the threshold. I will explain the exact rule in a moment.

Step five. The page is appended to a short history of the most recent eight pages. Then the predictor learns: it is told that the previous pages in the history were followed by this page.

Step six. The predictor is asked for predictions, given the updated history. It returns a list of candidate pages with confidences.

Step seven. For each candidate, if the page is already in RAM, it is skipped immediately, because prefetching it would do nothing. Otherwise the simulator builds a small description of the state, including how many frames are free, how many prefetches have been issued so far and how many requests have been processed, and asks the decision engine to decide.

Step eight. If the decision engine says yes, the memory engine's prefetch function is called, which installs the page through the same door as a fault, marks it as prefetched and unused, and counts one prefetch.

Then the loop moves to the next request, and repeats this for all two hundred thousand requests. At the end, the memory engine reports its counters: requests, faults, fault rate, evictions, prefetches, prefetches used, prefetches wasted, and precision. The decision engine adds its own statistics, such as its final threshold and how many epochs it was winning or losing. The script saves one row for this configuration to a results file immediately, so that if the run is interrupted, it can resume later without repeating finished work. When all configurations are done, the report script turns all the result files into an HTML report and opens it in the browser.

Notice one subtle but important detail. The predictor learns before it predicts, and it only ever learns from requests that have already happened. It never sees the future. That is what makes the simulation honest.

What happens in unusual situations? If a predicted page is already in RAM, it is skipped. If prefetch is called on a page that is already resident, nothing happens. If RAM still has a free frame, no eviction occurs. If the history is too short for a predictor's context, the predictor simply makes no prediction. If the same page is requested twice in a row, the readahead predictor ignores it, because it carries no information about direction. If someone accidentally passes the ghost-list decision engine to the wrong simulator function, the code refuses with an error, because otherwise it would silently behave as a different engine. That guard was added after the problem was discovered during verification.


PART FIVE. THE INTERNAL LOGIC IN DETAIL.

Now let's go inside each component and understand exactly how it works and why.

Let's begin with installing a page, because everything else depends on it. The install routine first checks whether the page is already resident; if so, it does nothing. If RAM is full, it asks the eviction policy to choose a victim, removes the victim from the resident set, tells the policy the victim has gone, and counts one eviction. If the victim was a prefetched page that was never used, it counts one wasted prefetch. Then it adds the new page to the resident set and tells the policy about the insertion. If the installation was a prefetch, it marks the page as prefetched and unused, and counts one prefetch. That is the entire door into RAM.

Now the LRU policy itself. It keeps an ordered dictionary, which is a structure that remembers the order in which keys were added and can move a key to the end in constant time. When a page is inserted or hit, it is moved to the end, the most recent position. When a victim is needed, LRU returns the first page in the dictionary that is still resident, which is the least recently used one. Both operations are effectively constant time, which matters because they run on every single request.

OPT is implemented efficiently. When it is created, it is given the whole trace, and it builds, for every page, a sorted list of the positions where that page appears. When a victim is needed, for each resident page it uses binary search to find that page's next appearance after the current position, and it picks the page whose next appearance is furthest away. If it finds a page that never appears again, it stops searching immediately, because nothing can be further than never.

Now the predictors. Let's start with the Markov predictor, because it is the original heart of the project. A Markov predictor is a table of counts. The idea comes from a classic research paper by Joseph and Grunwald in 1997 called Prefetching using Markov predictors. The table records, for each context, which pages followed it and how many times. The context is either the last page, which is called order one, or the last two pages, which is called order two.

Let's follow an example that the project actually ran. Take an order one Markov predictor and feed it the pages ten, twenty, thirty, ten, twenty, thirty, ten, twenty, forty, ten, twenty, thirty. At the start, the table is empty, so the first few requests get no prediction at all. After the first round, the table knows that ten was followed by twenty, twenty by thirty, and thirty by ten. So when the program asks for ten the second time, the predictor, before the next request arrives, predicts twenty with full confidence, and it is right. The same happens for thirty and ten. Then comes the irregular step. After twenty, the predictor predicts thirty, but the program asks for forty instead. That prediction is wrong. The next request comes after forty, a context never seen before, so there is no prediction at all. Then the pattern resumes. For the very last request, the table for context twenty contains two counts for thirty and one count for forty, so the predictor predicts thirty with a confidence of two out of three, which is about sixty-seven percent.

The project deliberately keeps these tables small, because the predictor runs on every request and its own cost counts against the time it saves. Each table holds at most two hundred and fifty-six contexts. When a new context arrives and the table is full, the least recently used context is removed. Each context keeps at most two successors, the two most frequent next pages. And every twenty-five thousand updates, every count is halved, and counts that reach zero are removed. Why halve? So that old behaviour fades away and the table follows what the program is doing now, not what it did long ago. These values were chosen on the warm-up data: prediction accuracy on the real traces was exactly the same from one hundred and twenty-eight entries all the way up to four thousand and ninety-six entries, so two hundred and fifty-six was plenty.

Now confidence. The confidence of a prediction is the count of the best successor divided by the total of all counts in that context. And here is something subtle the project discovered. Because each context keeps at most two successors, the best one always holds at least half of the counts. So confidence can never be below fifty percent. This is not a property of the programs; it is a consequence of keeping only two successors. Why does this matter? Because one of the early decision engines used a confidence threshold of thirty percent, and it behaved exactly like an engine that prefetches everything. Every prediction passed. The project initially reported "confidence cannot discriminate" as a finding about workloads, and then, during verification, corrected it: the floor is structural. That kind of self-correction is important to mention in a viva.

The stride predictor is much simpler. It looks at the last three gaps between pages. If all three gaps are equal and not zero, it predicts the last page plus that gap. For example, after the pages two, ten, eighteen, twenty-six, the gaps are eight, eight and eight, so it predicts thirty-four. It needs no table at all.

The hybrid predictor combines these. It asks the order two Markov table first, because it is the most precise. If that has no answer, it asks the order one table, which covers more situations. If that has no answer, it asks the stride predictor. The first answer wins. But here is an important detail: both Markov tables learn on every request, even when they are not the one answering. Why? So that after the program changes its behaviour, the table that was idle is already prepared to take over. On the first four real traces, the hybrid's top guess was exactly the next page about eighty-one percent of the time.

But the Markov predictor has a fundamental weakness. It memorises page numbers. It can only predict a page it has already seen. If a program reads through brand new data, page after page, the table has never seen those pages and cannot predict them. This is where the next two predictors come in.

The delta Markov predictor uses exactly the same table machinery, but over gaps instead of pages. Its context is the last two gaps, and its successor is the next gap. The predicted page is the last page plus the predicted gap. Let's follow the example the project ran. The pages are one thousand, one thousand and one, one thousand and four, one thousand and five, one thousand and eight, and so on. The gaps alternate: plus one, plus three, plus one, plus three. After the predictor has seen this gap pattern twice, it predicts one thousand and nine correctly, then one thousand and twelve, then one thousand and thirteen, then one thousand and sixteen, even though none of those pages had ever appeared before. A page-number table could never do that. A predictor called the delta hybrid places this delta table into the chain after the two page tables and before stride.

The readahead predictor models what the Linux operating system already does. It watches for sequential access. When two consecutive pages appear, such as one hundred followed by one hundred and one, it starts a stream and requests a window of the next pages. Each time the program reaches the middle of the requested window, it doubles the window and requests the next window. If the program jumps somewhere else, the stream is broken and everything resets. Let's follow the example the project ran with an initial window of two and a maximum of eight. The program reads one hundred, then one hundred and one: a stream starts, and pages one hundred and two and one hundred and three are requested. When the program reaches one hundred and two, which is the middle of that window, the window doubles to four and pages one hundred and four to one hundred and seven are requested. When the program reaches one hundred and five, the window doubles to eight and pages one hundred and eight to one hundred and fifteen are requested. Then the program jumps to page two hundred, and the stream resets. Real Linux caps the window at thirty-two pages, but that is larger than our entire simulated RAM, so the project caps the window at a quarter of RAM and starts with four pages, or less if RAM is tiny. Repeated requests for the same page are ignored.

In the final system, readahead candidates are given a confidence that grows with the length of the run: the run length divided by the run length plus one. So a run of one step gives fifty percent confidence, and a run of nine steps gives ninety percent. Why? So the decision engine can block short runs, which are often false alarms.

The final predictor, called the stream Markov predictor, combines readahead with the delta hybrid. Both parts learn from every request. When asked for predictions, it returns the readahead window first, and then the delta hybrid's guess if that page is not already in the window. The two parts cover different situations: readahead covers new pages in a sequential run, and the Markov tables cover repeating patterns, including gap patterns in new regions of memory.

Now let's turn to the decision engine. Here is its decision rule, in the order it is checked. First, if an optional off state is active, the answer is no. Second, if the number of prefetches so far exceeds a budget fraction of the number of requests, the answer is no. In the final system this budget is effectively switched off, for a reason I will explain in the results. Third, if RAM has at least one free frame, the answer is yes as long as the confidence is at least fifteen percent, because a wrong prefetch into a free frame evicts nothing and so costs almost nothing. Fourth, if RAM is full, the answer is yes only if the confidence is at least the current threshold. The threshold starts at fifty percent and can move between fifteen percent and ninety-five percent.

How does the threshold move? This is the feedback controller. Every epoch, which is every one thousand requests in the final system, the controller receives a number called the delta rate. The delta rate equals the faults we would have had without prefetching, minus the faults we actually had, during that epoch, divided by the epoch length. So a positive delta rate means prefetching saved faults, and a negative one means prefetching caused faults. If the delta rate is greater than two thousandths, the threshold is lowered by one step of zero point one, which makes the engine bolder. If the delta rate is below minus two thousandths, the threshold is raised by one step, which makes the engine more careful. If the delta rate is in between, which is called the dead band, nothing changes. The dead band stops the controller from reacting to random noise.

Let's walk through five epochs with the final settings. In the first epoch, the real system has one hundred faults and the shadow has one hundred and thirty. The delta rate is thirty divided by one thousand, which is plus three hundredths. That is above the dead band, so the threshold drops from fifty percent to forty percent. In the second epoch, the real system has one hundred and ten faults and the shadow one hundred and twenty-five. The delta rate is plus fifteen thousandths, so the threshold drops again, to thirty percent. In the third epoch, the real system has one hundred and twenty and the shadow one hundred and twenty-one. The delta rate is only one thousandth, inside the dead band, so nothing changes. In the fourth epoch, the real system has one hundred and forty faults but the shadow only one hundred and twenty. Prefetching is now hurting. The delta rate is minus two hundredths, so the threshold rises back to forty percent. In the fifth epoch, the real system has one hundred and fifty and the shadow one hundred and twenty. The threshold rises to fifty percent. You can see the controller following reality.

Why was this design chosen instead of something simpler? Because the project tested the simpler alternatives and they failed. A fixed confidence threshold cannot discriminate, because confidence never falls below fifty percent. A controller based on precision, meaning the fraction of prefetched pages that were later used, sounds sensible but is misleading. On the clustered test pattern with nine frames, four different engines achieved precision between eighty-one and eighty-six percent, which sounds excellent, and yet faults went up. How can a used prefetch be harmful? Because when it was loaded, it pushed out another page that was needed even sooner. The prefetched page was used, but the evicted page caused a fault. Precision only counts the first part of that story. The fault delta measures the actual outcome, which is why it works.

Now the hardest part: how do we know how many faults we would have had without prefetching? The project tried three answers.

The first answer is the oracle. Run a complete second copy of the memory engine on the same requests, without prefetching, and count its faults. This is exact, but a real operating system cannot keep a second copy of its memory, so it is not deployable.

The second answer is the ghost list, inspired by the ghost entries in ARC and by the shadow entries that Linux keeps for evicted pages. Whenever a prefetch evicts a page, remember that page's number and the time, in a list of two hundred and fifty-six entries. Whenever a fault occurs, check whether the faulting page is in that list and was evicted within the last two thousand requests. If so, count it as harm caused by prefetching. The estimated benefit is then the number of prefetches that were used, minus the harm. This costs only about four kilobytes. For the original Markov predictor, it worked as well as the oracle: an average gain of nine point zero two percent against eight point nine eight for the oracle.

But when readahead was added, the ghost list was fooled. On the clustered test with nine frames, it reported that prefetching was winning in twenty-four out of twenty-five epochs, with an estimated benefit of plus nine hundred and eighty-eight faults, while in truth prefetching was causing one thousand two hundred and fifty extra faults. The system ended up twenty-one point five percent worse than LRU. Why? The ghost list counts every used prefetch as a saved fault, exactly the same blind spot that made precision fail.

The third answer, which the final system uses, is the shadow directory. It is a copy of the eviction policy that runs on the same requests without prefetching, but stores only page identifiers, never page data. That costs about eight bytes per tracked frame, which is roughly two tenths of one percent of RAM when pages are four kilobytes. With every page tracked, its estimate equals the true fault delta in every single epoch, and the project has an automatic test that checks this. It can be made even cheaper by tracking only a sample of pages. A page is included in the sample if its number, multiplied by a large constant and reduced to thirty-two bits, falls below the sample rate times two to the power of thirty-two. With a sample rate of one in eight, the directory has one eighth as many frames, and the counted difference is multiplied by eight. This idea comes from a technique called SHARDS, published by Waldspurger and colleagues in 2015. In the project's tests at five percent memory, sampling one page in eight gave exactly the same fault counts as tracking every page on nine out of ten traces. With the shadow directory, the bad clustered case went from twenty-one point five percent worse than LRU to only two point five percent worse.

The project also tried adding an off switch: when prefetching keeps losing even at the highest threshold, turn it off completely and retry after one epoch, then two, then four, doubling each time. It never triggered on any program, so it remains disabled. It is reported honestly as a non-result.

Finally, the time model. Fault counts hide three things. Every prefetch is also a disk read. A prefetched page might be needed before its read has finished, which is called a late prefetch. And a demand fault might have to queue behind prefetch reads. The time model replays the event log on a simulated disk. Every request costs some computing time, which is unknown for these traces and is therefore tested at a tenth of a microsecond, one microsecond and ten microseconds. Every request that asks the predictor also costs two tenths of a microsecond of prediction time. Every disk read takes eighty microseconds on a modern NVMe solid state drive, which can serve eight reads at once, or five milliseconds on a hard disk, which serves one read at a time. A demand fault waits for its read, possibly behind earlier prefetch reads. A prefetch does not make the program wait, unless the program needs the page before the read finishes, in which case it waits for the remainder. The speed-up is the estimated time of LRU divided by the estimated time of the system.

Let's walk through two tiny examples the project tested. Suppose each read takes one unit of time, each request takes a tenth of a unit of computing, and there is one disk channel. In the first example, a page is prefetched at the first request and needed at the second. The read finishes at time one point one, but the page is needed at time zero point two, so the program waits nine tenths of a unit. In the second example, a page is prefetched at the first request and a different page faults at the second. The fault must wait for the prefetch read to finish on the single channel, and then take its own full unit, so the total time is two point one units. These two cases explain most of what you will see in the time results.

The project also computes a simpler quantity called the break-even cost. It is the number of faults saved compared with LRU, divided by the number of prefetches issued. It tells you the largest cost of one prefetch, measured as a fraction of the cost of one fault, at which the system still beats LRU. If the break-even cost is below one, then the system loses whenever a prefetch costs as much as a fault, which is exactly what happens on a single-channel hard disk.


PART SIX. THE SOURCE CODE AND THE KEY DECISIONS.

Let me now connect what you have learned to the actual code, so that you can talk about the implementation with confidence.

The config module is the single place for settings. It sets the page size through a twelve-bit shift, the cap of two hundred thousand requests, the warm-up fraction of twenty-five percent, the frozen predictor settings, which are a capacity of two hundred and fifty-six, two successors, order two, and halving every twenty-five thousand updates, and the frozen controller settings for the final system, which are an epoch of one thousand requests, a step of zero point one, a dead band of two thousandths, and a budget ratio of one point zero one, which means no budget cap. The comments in this module record why each value was chosen and on which data.

The traces module contains the six synthetic generators, a converter that reads compressed trace files, takes the third column of each line as a hexadecimal address, shifts it right by twelve bits to get the page number, and writes a simple comma-separated file, and a trace class that holds the page numbers, the gaps between them, and the warm-up split.

The engine module contains the memory engine class with its install, access and prefetch functions and its statistics, a ghost memory engine that adds the ghost list, and the six eviction policies. Every policy follows the same small interface: it is told when a page is inserted, hit or evicted, and it is asked to choose a victim. This shared interface is why any policy can be placed under any predictor.

The predictors module contains the Markov predictor, the stride predictor, the hybrid, the delta Markov predictor, the delta hybrid, the readahead predictor, a small wrapper that makes a predictor return its two best guesses, and the stream Markov predictor used in the final system. Every predictor follows the same interface: a predict function that takes the history and returns candidates with confidences, an update function that learns from the history and the actual next page, and a statistics function. A helper function builds predictors from the frozen settings, so no experiment can accidentally use different values.

The deciders module contains nine decision engines: one that never prefetches, one that always prefetches, three with fixed thresholds of thirty, sixty and eighty-five percent, the precision-based engine, the fault delta oracle, the ghost list engine and the shadow directory engine. The last three share a single controller function, so they differ only in where their fault delta comes from, which makes their comparison fair.

The simulate module contains a function that measures prediction quality on its own, and three simulation loops. The first is used with the simple engines and with the oracle. The second is used with the ghost list. The third is used with the shadow directory. All three follow the eight steps you learned earlier, in exactly the same order. A small function decides whether a page belongs to the shadow directory's sample.

The timing module contains the time model's replay function. It keeps the free times of the disk channels in a small priority queue, so the earliest free channel can always be found quickly.

The final module defines the final system in three short functions: one builds the final predictor, one builds the final decision engine from the frozen controller settings, and one runs the shadow directory loop with them.

Let's now go through the key design decisions and why each was made, because examiners love to ask why.

Why a simulator and not a kernel? Because it gives identical input to every method, perfect reproducibility, the ability to compute OPT, and far less engineering effort.

Why Markov tables and not deep learning? Because the predictor runs on every single memory request. A lookup in a small table costs almost nothing and the whole predictor fits in a few tens of kilobytes. A neural network would cost far more per request. A comparison with a learned predictor is fair future work.

Why size memory as a percentage of the working set? Because with large fixed memory, nothing is evicted and every policy looks identical.

Why add prediction on top of LRU rather than replace LRU? Because the early results showed that the gain from prediction was about the same on FIFO, Clock and LRU, between thirty-four and a half and thirty-eight and a half percent on the two regular programs. Prediction adds to any eviction policy.

Why one door into RAM? Safety. Why separate the predictor and the decision engine? Fair comparison. Why tune only on warm-up data? Honesty.


PART SEVEN. HOW THE PROJECT GREW, PHASE BY PHASE.

It helps to understand the project as a story, because each phase answered a question and raised the next one.

Stages one and two collected and prepared the data. Stage three built the predictors and chose their settings. Stage four built the memory engine and checked it automatically: no policy may beat OPT, more memory must never mean more faults for LRU or OPT, and a sequential scan must fault every time. It also showed how much room there was to improve: on leslie3d with twenty-one frames, LRU had fifteen thousand three hundred and thirteen faults while OPT had only five thousand eight hundred and eighty-one.

Stage five built the decision engines and compared them. This is where the project found that confidence cannot discriminate, that precision misleads, and that the fault delta works best. The fault delta engine halved the worst-case damage, from minus one and a half percent for the always-prefetch engine to minus seventy-two hundredths of a percent, while keeping almost all of the benefit. In a head-to-head comparison, adding prediction to LRU reduced faults on leslie3d from fifteen thousand three hundred and thirteen to nine thousand nine hundred and fifty-six, which is thirty-five percent fewer, and on bwaves from three thousand one hundred and forty to one thousand nine hundred and sixty-nine, thirty-seven percent fewer, which is even below OPT's three thousand one hundred and twelve, because prefetching avoided compulsory faults. The graph programs gained almost nothing, because more than ninety-nine percent of the predictions named pages that were already in RAM.

Then came verification. The project was moved from a Google Colab notebook into a proper code repository with tests, the traces were downloaded again, and everything was rerun. All forty-eight rows of the original decision engine results came out exactly identical.

Phase eight added stronger baselines: ARC, LRU-2 and Linux-style readahead. ARC and LRU-2 did not help on these traces. On leslie3d, ARC had sixteen thousand five hundred and fifty-three faults, more than LRU. And then came a real surprise. Linux readahead beat the Markov predictor on three of the four original real programs. On bwaves, readahead had only two hundred and four faults while Markov had one thousand nine hundred and sixty-nine. This changed the direction of the project. The reason was clear: readahead fetches new pages in a run, which Markov can never predict.

Phase nine tried to make eviction smarter, by evicting unused prefetched pages early and by protecting the page the predictor expects next. None of these ideas beat plain LRU on the warm-up data. Protecting prefetched pages for longer made things much worse, because it pushed out pages the program really needed, and protecting the predicted page changed nothing, because LRU already keeps recently used pages. That is a negative result, and it is reported honestly. Instead, readahead and Markov were combined into one predictor, which cut leslie3d to eight thousand three hundred and eight faults, better than either alone.

Phase ten improved the predictor. The delta Markov tier was added, which cut Markov alone on bwaves from one thousand nine hundred and sixty-nine faults to eight hundred and ten. Prefetching the two best guesses instead of one gave a big win on leslie3d but made bfs-3 about twenty percent worse, so it was not adopted. Smoothing the confidence values made things slightly worse, and requiring longer runs before readahead starts lost the graph gains, so both were rejected.

The next phases tested robustness on more programs, computed the break-even cost, let the decision engine gate readahead, built the shadow directory, built the time model, tuned the controller, and finally evaluated everything on twenty-two programs.

The tuning phase deserves a moment. Thirty-six combinations of epoch length, step size and dead band were tried, using only the warm-up portions, with the rule for choosing the winner written down in advance. The winner reacts every one thousand requests with steps of zero point one, instead of two thousand requests and steps of zero point zero five. It halved the warm-up worst case, from minus eight percent to minus three point eight percent. Interestingly, only the two programs where prefetching can hurt changed at all; the other twelve were identical. That makes sense: the controller only matters when prefetching is dangerous.

The final evaluation also uncovered a hidden problem. The early decision engines had a safety cap that limited prefetches to thirty-five percent of requests. On the omnetpp program, the final system hit that cap at exactly seventy thousand prefetches while its controller was winning in all two hundred epochs. The cap was blocking a clearly beneficial behaviour. On the warm-up data, removing the cap raised omnetpp's fault reduction from fifty-six percent to ninety-seven percent and made no program worse, so it was removed.


PART EIGHT. TWO COMPLETE EXAMPLES, START TO FINISH.

Let's now put everything together with two complete examples.

The first example is small enough to follow in your head, and the project computed it with its real code. Imagine a program that loops over five pages, one, two, three, four and five, three times in a row, so fifteen requests. RAM has only four frames. The predictor is the hybrid Markov predictor, and the decision engine is the one that always prefetches.

First, think about plain LRU. The loop is one page larger than RAM. So every time a page is needed, LRU has just evicted it, because it was the least recently used. Plain LRU faults on all fifteen requests.

Now follow the system with prediction. Requests one, two and three fault, because RAM starts empty. At the fourth request, page four, there is a fault too, but now the history is one, two, three, four, which has three equal gaps of plus one, so the stride part predicts page five. RAM is full, so prefetching page five evicts page one. The fifth request, page five, is a hit, because it was prefetched. But now the stride part predicts page six, which does not exist in the loop. That is a wrong guess, and prefetching it evicts page two. The sixth request is page one, which faults, because page one was evicted when page five was prefetched. From this point on, the order one Markov table has learned that five is followed by one, one by two, and so on, so every prediction is correct and every remaining request is a hit. Page two, which the wrong guess evicted, is brought back by a correct prefetch before it is needed, so the wrong guess wasted a disk read but did not cause an extra fault. The final count is five faults instead of fifteen. And notice that this tiny example contains both sides of the bet: correct prefetches that eliminate faults, and a wrong prefetch that evicts a useful page. That is exactly why the decision engine exists.

The second example is a real run that the project performed on the leslie3d trace, using its two hundred thousand requests and twenty-one frames, which is one percent of its working set. Plain LRU suffers fifteen thousand three hundred and thirteen faults. OPT, the theoretical best eviction, suffers five thousand eight hundred and eighty-one. The final system suffers eight thousand one hundred and thirty-three faults, which is forty-six point nine percent fewer than LRU. Along the way it issued sixteen thousand nine hundred and forty-six prefetches, of which seven thousand seven hundred and fourteen were used, a precision of forty-five and a half percent. Its decision engine ended at the lowest threshold of fifteen percent and was winning in all two hundred epochs, which means the feedback consistently said prefetching was helping. The whole run took about one point two seconds on a laptop. You might wonder how fewer than half the prefetches being used can still remove nearly half the faults. The answer is that readahead fetches whole windows of pages; not every page in a window is used, but the ones that are used each remove a fault. The extra reads are the price, and that price is exactly what the time model measures.


PART NINE. TESTING, RESULTS, NOVELTY AND LIMITATIONS.

Let's talk about how we know the simulator is correct. The project has twenty-four automated tests, run with a tool called pytest, and they all pass. They fall into four groups. Invariant tests check rules that any correct implementation must obey: no policy may beat OPT, LRU and OPT must never get worse with more memory, with ample memory the number of faults must equal the number of distinct pages, and a sequential scan without prefetching must fault every time. Equivalence tests check that every new feature, when switched off, reproduces the old behaviour exactly. Pinned-number tests check exact fault counts on a fixed synthetic trace, so that any accidental change in behaviour is caught immediately. And component tests check specific behaviours, such as the delta Markov predictor predicting unseen pages, the shadow directory matching the true fault delta in every epoch, and the time model charging late prefetches and queueing correctly. Beyond the tests, independent straightforward implementations of LRU, FIFO and OPT were written and compared with the simulator on forty random traces, with zero mismatches, and the original Colab results were reproduced exactly.

Now the results, all measured. Over forty-four tests, twenty-two real programs at one percent and five percent memory, the final system removes on average fifty-five percent of LRU's faults. Its median is about fifty-nine percent. It is worse than LRU in only one test, bwaves-s2 at one percent memory, which has only eight frames, and there it is three point three percent worse. Linux readahead alone removes about fifty-one percent on average, but its worst case is nineteen point three percent worse than LRU. The original Markov system removes under eight percent. ARC on its own is about half a percent worse than LRU on average. The final system has fewer faults than readahead in thirty-four of the forty-four tests, the same in eight, and more in two. It has fewer faults than OPT in thirty of the forty-four tests, which, as you know now, is possible because prefetching avoids compulsory faults. Its biggest loss to readahead is the sphinx3 speech recognition program at one percent memory, where the decision engine holds back useful readahead.

When each component is changed one at a time, two lessons appear clearly. First, prediction accuracy and fault reduction rank the predictors almost in opposite order. Readahead names the exact next page only about three percent of the time, yet it removes forty-six and a half percent of faults on its own, more than any other single predictor, because it fetches pages nobody has seen yet. The delta hybrid is right about the next page fifty-nine percent of the time but removes only about twenty-one percent. Second, the decision engine matters most in the dangerous cases. The always-prefetch engine gets the full benefit on the real programs, but on the clustered test it is twenty-one and a half percent worse than LRU. Fixed thresholds are safe but throw away half or more of the benefit. The final engine keeps the full benefit and limits the clustered damage to about two and a half percent.

Now time. In the time model with one microsecond of computing per request, on an NVMe solid state drive the final system is about one point four three times faster than LRU, and readahead is about one point four four times faster, so they are level. The original Markov system is about zero point nine seven, slightly slower than LRU, even though it removes thirty-five to thirty-seven percent of faults on leslie3d and bwaves. Why? Because it prefetches only one request ahead, so its pages often arrive too late; on those programs, sixteen to twenty-two percent of the running time was spent waiting for late prefetches. On a single-channel hard disk, every prefetcher is slower than LRU: the final system is about zero point seven, readahead zero point eight, and Markov zero point nine three, because each prefetch read costs as much as the fault it tries to save, and every break-even cost was below one. These time figures come from a model with stated latencies, not from measurements on real hardware, and you should always say so.

So were the objectives achieved? The simulator is correct and reproducible. The predictors and decision engines were built and compared. The right feedback signal was identified and made cheap and deployable. The evaluation covered twenty-two real programs without tuning on test data. The one objective that is only partly achieved is speed: the system is faster than LRU on parallel storage, but only level with readahead, and slower on a hard disk. That is an honest finding, not a failure.

What is genuinely new? Be careful and honest here, because examiners test this. The building blocks are known. Markov prefetching comes from Joseph and Grunwald in 1997. Adapting to the fault rate resembles the Page Fault Frequency algorithm. Low-priority insertion of prefetches resembles a technique called PACMan. Ghost entries come from ARC and from Linux. Hash sampling comes from SHARDS. What this project contributes is, first, an evaluation of which feedback signal a cost-aware prefetcher should use, showing why confidence and precision fail and the measured fault delta works; second, an exact and cheap way to obtain that signal with a page-identifier-only shadow directory that can be sampled; third, the combination of readahead and delta Markov prediction with the largest fault reduction of every system tested; and fourth, a time-aware evaluation showing when fewer faults do and do not mean faster programs.

What are the limitations? The traces are processor-cache traces treated as pages, so they approximate operating-system paging. The predictor sees every memory request, which a real kernel does not; a kernel sees only faults and accessed bits, so our predictor has more information than a real one would, and the prediction cost we charge is an upper bound. The time results come from a model. Each trace has two hundred thousand requests and the simulated memories are small, between eight and one thousand one hundred and sixty-three frames. ARC is implemented without one textbook tie-breaking rule, LRU-2 without a correlated-reference period, and the readahead window is capped at a quarter of RAM. And each configuration was run once, which is acceptable because the traces are deterministic, so a rerun gives identical numbers; robustness comes instead from many programs and memory sizes.

What could be done next? These are suggestions, not implemented work. Evaluate on real operating-system page-fault traces or inside a kernel. Add priority for demand reads and control of how far ahead to prefetch, which would address late prefetches. Compare against a learned predictor such as a neural network under the same time model. Validate shadow-directory sampling at realistic memory sizes of millions of frames. And recover the gains the cautious decision engine leaves behind on programs like sphinx3. A paper draft has been written for a student or regional conference, framed as an evaluation study; acceptance is not assumed.


PART TEN. THE WHOLE SYSTEM IN ONE PICTURE, AND YOUR TWO-MINUTE EXPLANATION.

Let's step back and see everything as one connected system.

A real program's memory requests arrive one at a time. The memory engine checks whether each requested page is in RAM; if not, a fault occurs and LRU makes room. The predictor learns from the request and proposes candidates, with readahead covering new pages in a sequential run and the delta Markov tables covering repeating patterns. The decision engine accepts a candidate only if its confidence passes a threshold, being generous when RAM has free space and careful when it is full. Accepted pages enter RAM through the same single door as faults, so the system can never become incorrect. Meanwhile, a shadow directory replays the same requests without prefetching, storing only page identifiers, and every thousand requests the controller compares the two fault counts and makes the decision engine bolder or more careful. At the end, faults, prefetches and an event log are reported, and the time model turns the event log into an estimated running time. Every setting was chosen on the first quarter of each trace, and the whole thing is verified by twenty-four automated tests.

And here is a natural two-minute explanation you can use in a viva or presentation.

"Programs keep the data they are using in RAM and the rest on disk. When a program needs data that is not in RAM, it has to wait for the disk; that is a page fault. Our project is a simulator that replays the memory requests of real programs and tests whether we can avoid those waits by predicting the next pages and loading them early, which is called prefetching. The difficulty is that RAM is usually full, so every page we load early pushes another page out, and a wrong guess can actually cause a fault. So we built two parts. The first is a predictor, which combines Linux-style readahead for sequential reading with a Markov model that learns repeating patterns, including patterns in the gaps between pages, so it can predict pages it has never seen. The second is a decision engine that only prefetches when it is worth it. It learns from feedback: every thousand requests it compares how many faults we had with how many we would have had without prefetching, and becomes bolder or more careful. We found that the obvious signals, the predictor's confidence and the fraction of prefetches that get used, are misleading, and we measure the real difference cheaply with a shadow directory that stores only page names. On twenty-two real programs, our system removes about fifty-five percent of the page faults of the standard LRU policy, more than any other method we tested, and it is worse than LRU in only one of forty-four tests. But when we model time, it is about one point four times faster on a fast SSD, the same as Linux readahead, and slower on a hard disk, because fewer faults also means more disk reads and some prefetches arrive late. Understanding when prediction actually saves time, and not just faults, is one of our main contributions."
